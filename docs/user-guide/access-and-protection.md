# 利用者の識別とデータの保護（利用組織がすること）

> 本システムは「**誰が操作しているか**」を組織の ID 基盤に委ね、「**データそのものの保護**」を
> 端末と同期先の設定に委ねている。本書はその**利用組織側でやること**を書く。

## 1. 利用者 ID の前提（共用アカウントで使わない）

共同プロジェクトの作業者は、**利用者 ID**（組織メール / UPN）で識別する。
利用者 ID は初期設定で本人が登録し、**登録した端末の OS アカウントと結びつく**。
**画面には「メールアドレス（利用者 ID）」と表示される**。

利用組織側の前提:

- **担当者ごとに個人の OS アカウント**があり、本人がログオンして使うこと。
- 各担当者が**組織メール / UPN を持っている**こと。

**共用の OS アカウント（部署共通のログオン等）ではこの識別が成立しない**。
誰の操作なのかを記録・追跡できなくなるため共同プロジェクトを共用アカウントで使わないこと。

利用者 ID は本人の自己申告で登録するため**他人の ID を登録することも技術的には起こりうる**。
本システムは端末ごとの初回オープン時に「OS アカウント ⇔ 利用者 ID」の組を変更履歴へ記録するので、
**事後の追跡はできる**が、事前に防ぐのは利用組織側の運用（個人アカウントの割り当てと 3 章の保護）である。

- 登録した利用者 ID は**本人では変更できない**。改姓等で組織メール / UPN が変わったときは、
  プロジェクトのオーナーが訂正する。
- 同じ担当者が複数の端末（macOS と Windows の併用を含む）から、同じメンバーとして作業してよい。

## 2. アプリの権限判定でできること・できないこと

共同プロジェクトのメンバーには**オーナー / 編集 / 閲覧**の権限を割り当てる。
メンバーでない利用者はプロジェクトを開けない。権限ごとの主な操作は次のとおり。

| 操作 | オーナー | 編集 | 閲覧 |
|---|---|---|---|
| メンバーの追加・削除・権限変更・オーナー移譲、メンバーの利用者 ID の訂正 | ○ | ×（オーナー不在のときだけ、確認操作を経て引き継げる） | × |
| プロジェクトの削除・同期先の設定と変更・AI 利用量の上限の設定 | ○ | × | × |
| 編集の操作（対話・承認・資料の取り込み・質問票の発行と取り込み・生成・確定と差し戻し・名簿の管理）・同期先への反映・予約の設定と解除 | ○ | ○ | × |
| 参照（対話履歴・要件・成果物・変更履歴・AI 送信履歴・利用量）・進捗レポートの生成・同期先からの取り込み | ○ | ○ | ○ |

**ここで理解しておくこと**: アプリの権限判定が保証するのは
「**アプリの画面からその操作をさせない**」ところまでである。

- プロジェクトのデータは各メンバーの端末に**普通のファイルとして置かれている**。
  閲覧権限のメンバーの端末にもそのプロジェクトのデータは置かれる。
- そのため**アプリを使わずにファイルを直接読む・複製することは、権限判定では防げない**。
- 「閲覧権限にしたから内容を見られない」ではなく、「閲覧権限にしたから**アプリからは編集できない**」が正しい理解である。

データそのものの保護は次の 3 章で行う。

## 3. 端末側の保護と同期先側のアクセス制御（二層で守る）

本システムのデータは **(a) 各メンバーの端末** と **(b) 同期先** の 2 か所にある。
**両方**に保護をかけること。片方だけでは、もう片方からデータを読めてしまう。

| 場所 | 利用組織がすること |
|---|---|
| **端末**（各メンバーの作業コピー） | OS のアカウントを担当者ごとに分ける（他人のプロファイルのファイルを読めない状態にする）／**ディスクの暗号化**（FileVault / BitLocker）を有効にする／端末の紛失・退職時の回収と失効の手順を持つ |
| **同期先**（共有フォルダ / Git サーバ） | プロジェクトの関係者だけがアクセスできるように**共有フォルダの ACL**、または **Git サーバ側の権限設定**を行う／退職・異動時にアクセス権を外す |

**同期先を外部の Git サービスに置く場合**は、要件定義の内容（対象システムの業務情報を含む）が
**組織の外が運用するホストに保管される**。組織のセキュリティポリシーに適合するかは利用組織の判断であり、
本システムは設定時に同意を求めるだけである。
既定は**組織内の共有フォルダ**である。

### 共有フォルダ（SMB / NAS）を同期先にする場合の注意

**同時に反映したときの安全性が、この経路だけ未検証である。**

本システムは 2 人が同時に反映しても片方が確実に拒否されること（＝**後から反映した側が
先の変更を消さない**こと）に依存している。この排他は OS のファイルロックで成り立っており、
**ネットワーク越しのファイル共有ではそのロックが期待どおりに働かないことがある**。

- **Git サーバ**（社内外の Git ホスティング）を同期先にする場合はこの問題は起きない。
  同時に反映しても先の変更が消えないことを検証済みである。
- **共有フォルダ（SMB / NAS）**を同期先にする場合は、**実際に使う共有フォルダで確認するまで
  安全とは言えない**。確認の手順と道具はリポジトリに用意してあるが、
  **検証環境が用意されていないため未実施**である。

**当面の運用**（確認が済むまで）:

| やり方 | 可否 |
|---|---|
| 同期先を **Git サーバ**にする | **推奨**。検証済み |
| 共有フォルダを同期先にし、**メンバーごとに別のブランチ**で運用する | 可。同一ブランチへの同時反映が起きないため原理的に競合しない |
| 共有フォルダを同期先にし、**全員が同じブランチへ反映**する | **確認が済むまで避ける**。どうしても使う場合は、反映のタイミングを口頭で分ける（同時に押さない）運用にする |

> シークレットキー（AI プロバイダのキー）と同期先の認証情報は、**端末ごと**に OS のセキュアストレージへ
> 保管され、メンバー間で共有・受け渡しをしない。
> 「1 つのキーをチームで共用する」運用は想定していない。
